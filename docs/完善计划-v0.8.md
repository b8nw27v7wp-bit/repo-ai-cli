### 两处与本文原稿的偏差（均已在实现中说明）

1. **P0-2 用 `minor` 而不是 `major`**。原稿写「破坏性变更，需 changeset major 说明」，但实现保留了旧名作为可用别名，运行时完全向后兼容——按 semver 这不算 breaking。真正的破坏发生在「下个 major 移除旧名」那一步，changeset 里已写清。若坚持现在就走 major（0.x → 1.0.0），改一行 changeset 即可。
2. **P1-1 为保住「纯搬迁」而多花了一点结构成本**。`--help` 的命令顺序也是 README「Command Options」的小节顺序；按「AI 命令整块在前」的自然拆法会改掉这个顺序，于是改为「一命令一注册器 + `program.ts` 里显式写死 `COMMAND_ORDER`」。换来的是可证明的无副作用重构：拆分前后对 `--help` 与 33 个叶子命令的 `--help` 做了逐字节 diff，结果一致。

### 执行中新发现的问题

**P0-3（新增，未做）`config set` 的 5 个键是只写键。** 实测：`config set maxTokens/maxFileKb/maxDiffKb/maxOutputTokens/temperature` 保存成功、`config list` 显示、`config.ts` 的 label 写着「readme 默认 token 预算」，但**没有任何命令读取它们**——`grep -rn "cfg\.\(maxTokens\|maxFileKb\|maxDiffKb\|maxOutputTokens\|temperature\)" src/` 零命中，只有 `provider`/`baseUrl`/`model`/`apiKey` 经 `llmConfigFromOptions` 真正生效。用户以为设了默认值，实际命令仍走各自的 flag 默认值。

不修的原因：修它要先决定「各命令的默认值该放哪」。现在 temperature / max-output-tokens 的默认值按命令不同（0.3 / 0.5 / 0.7、1024 / 2048 / 4096 / 8192），写在 `register-ai.ts` 的 commander 默认值里；要让配置生效，必须靠 `getOptionValueSource()` 区分「用户传的」与「默认值」，或把默认值从 CLI 层搬进命令层。两种都要动 12 条命令 + types + README 的默认值表，属于独立的一块工作，不该夹在参数改名里做。

**P0-4（新增，已修）`release --bump --tag` 的失败残留。** 原实现先改 `package.json` 版本号、再检查 tag 是否已存在，于是「tag 已存在」这条失败路径会把版本号留在已 bump 的状态——命令报错退出，工作区却被改过了。改由 tag 冲突先判、通过后才 bump。这是补命令层测试时被用例抓出来的（用例断言「失败后版本号不变」直接变红）。

**P0-5（新增，未做）密钥检测的已知漏报。** `collect-files.ts` 的 `isPlausibleSecret` 把「纯小写+连字符」的值当人写词组放行（该文件注释里已写明这一取舍）。实测漏报例：`{"apiKey": "sk-live-9f3a2b7c1d4e5f60"}` 会被放行并随材料发给 LLM。可行的收窄方向是「连字符分段里出现数字即不算词组」（`use-environment-variable` 全字母放行，`sk-live-9f3a2b7c1d4e5f60` 拦下），但会牵动既有的 collect-files 测试与那条刻意为之的取舍，需单独评估误杀率后再改。

**P0-6（新增，已修）`package-lock.json` 版本号漂移。** 锁定文件停在 `0.6.0`，`package.json` 已是 `0.7.0`。已在本次一并同步。

### 1.3 结构性短板（本次计划的直接依据）

**短板 1：命令层测试缺口。** 16 个命令没有同名测试文件：

```
ask  commit  explain  fix  gitignore  init  license  pr
readme  refactor  release  review  review-pr  test  translate
```

能力并非没测（prompt 组装、collect-files、token-budget 都有专项），缺的是**命令层**：参数如何流转、`--json` 是否静默、失败时退出码是否为 1、`--output` 落盘路径是否正确、非 TTY 行为。而这类漏洞恰恰出过多起——`secrets --json` 命中曾缺退出码 1（CI 门禁失效）、`changelog` 非法 `--format` 曾多打一行进度输出。**这类问题只有命令层测试能守住。**

**短板 2：参数命名三套并存。** 同一类「给 LLM 的材料预算」有三种写法：

| 命令 | 参数 | 含义 |
|---|---|---|
| readme / ask / fix | `--max-tokens` | 收集文件的 token 预算 |
| commit / review / review-pr / pr | `--max-diff-kb` | diff 的 KB 预算 |
| changelog | `--max` | 提交条数 |
| explain / translate / test / refactor | `--max-file-kb` | 单文件 KB 上限 |

用户从 readme 换到 changelog 时「预算」突然变成条数，从 readme 换到 review 时单位从 token 变成 KB。**这是本 CLI 目前最影响上手体验的一致性问题。**

**短板 3：`src/index.ts` 859 行，是全仓库最大文件。** 24 条命令的注册、共有 option 组、错误处理都挤在一处。继续加命令会让它成为瓶颈，也难 review。

**短板 4：无回归用的端到端基线。** 298 条单元测试没有一条「对固定 fixture 仓库跑完整命令序列并断言输出」的用例。重构时只能靠单测，跨命令的破坏（如 `ui.ts` 改动影响所有命令）发现不了。

**短板 5：LLM 交互无成本可观测性。** 用户按 token 付费，但 CLI 从不在回答里告诉用户「这次调用消耗了多少 token、估计多少钱」。`llm.ts` 收到了 `usage` 却只在内部丢弃。

## 二 本期目标与原则

工程侧已经扎实（298 测试、严格类型、CI 门禁、docs 自动校验）。**横向铺命令的时代结束**——目标用户不会因为第 25 条命令改变选择。本期三条主线：

1. **守住已有的**：把命令层测试缺口补上，让「能工作的功能」持续能工作
2. **磨一致性与可维护性**：参数命名统一、超大文件拆分，为后续演进铺路
3. **补高价值能力**：成本可观测（用户按 token 付费，却看不到消耗）、PR 审查闭环

**明确不做**（防范围蔓延）：GUI / VSCode 插件、自建代理或云端托管、AI 直接写代码（`test`/`refactor`/`fix` 保持只给建议）、非 GitHub 托管平台支持。

## 三 计划清单（按优先级）

### P0-1 命令层测试补全（最高优先，零风险）

为 16 个缺测试的命令补命令层测试，只测**接线与契约**，不重测底层逻辑（底层已有专项覆盖）：

每个命令固定覆盖四点：
1. 非法枚举/缺参数 → 退出码 1 且报错可读
2. `--json` 模式下 stdout 只有 JSON，进度与告警不泄漏
3. 失败路径（LLM 抛错 / 文件不存在）→ 退出码 1 且不写半成品
4. `-o/--output` 落盘到指定路径

分批推进，每批 4 个命令、跑一次门禁。**优先补 AI 命令**（接线更复杂、有 LLM 失败路径）。

### P0-2 预算参数命名统一（破坏性变更，需 changeset major 说明）

统一为一个语义清晰的参数族，旧名保留为隐藏别名并 deprecation 提示：

| 现参数 | 改为 | 适用范围 |
|---|---|---|
| `--max-tokens`（readme/ask/fix） | `--budget-tokens` | 收集材料的 token 预算 |
| `--max-file-kb`（readme/ask/fix/explain/translate/test/refactor/secrets） | `--max-file-kb`（不变） | 单文件 KB 上限 |
| `--max-diff-kb`（commit/review/review-pr/pr） | `--max-diff-kb`（不变） | diff KB 上限 |
| `--max`（changelog 条数） | `--max-commits` | 提交条数 |

即只改两处：`--max-tokens` → `--budget-tokens`、`--max` → `--max-commits`；旧名接受但打 deprecation 警告，下一个 major 移除。README 与 docs:check 同步。

**为什么值得做破坏性变更**：0.6.x 仍在快速迭代期（月下载 71），越早统一成本越低；到 1.0 再改就是真破坏。

### P1-1 `src/index.ts` 拆分（859 行 → 目标 300 行以内）

按职责拆出：
- `src/cli/register-ai.ts` — 11 条 AI 命令的注册 + 共有 LLM option 组
- `src/cli/register-offline.ts` — 13 条离线命令注册
- `src/cli/program.ts` — program 组装、全局 option、preAction hook

保持 `src/index.ts` 作为薄入口。**纯搬迁不改行为**，完成后 diff 应只有 import 路径变化。

### P1-2 端到端回归基线

新增 `scripts/e2e-smoke.mjs` + `npm run e2e`：在构建产物上跑一条固定命令序列，对固定 fixture 仓库断言退出码与关键输出，不进单元测试套件（耗时且需 dist）。纳入 CI。

这是「删掉 16 个命令里任意一个的错误接线」能被抓住的唯一手段。

### P1-3 Token 成本可观测（`llm.ts` 已有 usage，只差呈现）

- `llm.ts` 从响应里取出 `usage.prompt_tokens` / `completion_tokens` / `total_tokens`
- 非 `--json` 模式下向 stderr 打一行汇总：`token 用量: 输入 1234 / 输出 567 / 合计 1801`
- `--json` 模式并入输出对象的 `usage` 字段
- 不做价格换算（模型价格多变，换算必然过期，属于「写死会错的数据」）；仅在 README 说明如何自行估算
- 补测试；流式路径同样要统计（SSE 的 usage 在末帧，需处理缺失情况）

### P2-1 review-pr 审查闭环（PR 上留评论）

当前 `review-pr` 只输出报告，用户要复制粘贴回 GitHub。补 `--comment`：

- 需要 `GITHUB_TOKEN`（已有读取逻辑，`github-pr.ts` 的 `apiHeaders`），缺 token 时给出获取指引
- 以 PR review comment 形式提交，按严重程度分级逐条发（Critical/Major 作为独立 comment，Minor/Nit 合并为一条）
- 默认 dry-run：只打印将要发布的内容，加 `--comment --yes` 才真发
- 危险动作必须有确认：交互模式 confirm，非交互必须显式 `--yes`

### P2-2 采用面（非代码）

- 修复 npm 月下载停滞的下一个可能因素：package.json 的 keywords 覆盖（当前 topics 已有 15 个，关键词与 topics 对齐可提升 npm 搜索命中）
- README 补「与其他工具的对比」一节（同赛道 readme-ai / cz-cli / commitizen），如实写明定位差异——不贬低竞品，只讲清「BYOK + 24 条命令 + 离线可用」的取舍
- GIF 已交付录制指南；若用户录制完成，替换 README 占位行

### 附录 A-1 拆分「零行为变更」的证明方式

```bash
# 拆分前后各抓一次全部 --help（顶层 + 33 个叶子命令），逐字节 diff
node dist/index.js --help > before.txt
for c in $(node dist/index.js --help | sed -n '/^Commands:/,$p' | grep -oE '^  [a-z-]+' | tr -d ' '); do
  echo "### $c" >> before.txt; node dist/index.js $c --help >> before.txt
done
# 拆分、重建后重复一次，diff before.txt after.txt —— 无输出即为通过
```

这比「跑一遍 e2e 没报错」强：e2e 只覆盖被断言到的那几条命令，逐字节 diff 覆盖全部 34 个 help 输出。
