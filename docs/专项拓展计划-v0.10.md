### 执行中的实现取舍

1. **`repo-index` 直接建立在 `collectFiles()` 之上**，没有再写一个 walker：它是本仓库唯一的收集入口，文件名级敏感过滤与 .gitignore 语义都可以直接复用。代价是索引只覆盖可分析文件（源码/配置/文档），图片等二进制本来也不需要。`collectFiles` 新增了 `onSizeSkipped` 回调，`health` 用它统计大文件。
2. **ESM 的 `.js → .ts` 映射是必须的**：本仓库源码是 `.ts`、import 写 `./x.js`，只看扩展名会 379 处全部解析失败。修复后本仓库 `unresolved` 降到 3。
3. **`health` 发现本仓库有 1 处 high 疑似密钥**（来自 `test/*.test.ts` 的密钥 fixture，即交接文档 §五记录的「secrets 对自己误报」）。这是真实行为，不为了「自己全绿」而调低阈值。
4. **`onboard` 的展示名优先取 `package.json` 的 `name`**：worktree 目录名（`merge-commit-push-...`）出现在文档里没有意义。

### 代码审核与边界测试后的修正（2026-10-17）

审核用临时 fixture 复现并修复了 6 个问题，测试 484 → **505**：

1. **离线索引不再做内容级密钥过滤**。`collectFiles` 新增 `contentSecretScan`（默认 true），`repo-index` 传 false：索引只保存路径/行数/import 边，从不外发内容；此前的过滤会把含测试密钥 fixture 的测试文件排除掉，本仓库 `impact src/lib/scan-secrets.ts` 因此漏掉 `test/scan-secrets.test.ts`。发给 LLM 的材料路径（`collectMaterials`）仍保持内容过滤。
2. **`impact --diff` 支持删除与重命名**。新增 `getStagedChanges()`（`git diff --cached --name-status -z`），重命名同时拿到新旧路径；`computeImpact` 会把已不在工作区的目标当作虚拟节点，重新解析其他文件的 raw import。此前暂存区只有删除时会直接报「变更文件都不在索引中」。
3. **解析 Python 的 `from . import name`**。此前模块部分只有点，真正的目标在 import 后面，`from . import utils` 的依赖边会丢失。
4. **`health` 区分 package.json 缺失与损坏**。此前坏 JSON 被当成「非 Node 项目」跳过，健康检查全绿；现在记为 `fail`，依赖清单检查也明确提示跳过原因。
5. **`health` 补查 package.json 的 `name`**。缺 `name` 的包无法发布，属于元数据硬伤。
6. **`map --focus` 接受绝对路径**。Windows 的 `path.relative` 返回反斜杠，而索引路径是 `/`，此前传绝对路径会一个文件都匹配不上；现在统一转成 POSIX，跨盘符则明确报「必须位于仓库内」。

### 1.2 能力分布：24 条命令都是「单任务」视角

**AI 命令（12 条）**：readme / commit / changelog / review / review-pr / explain / pr / translate / test / refactor / ask / fix
**离线命令（12 条）**：init / secrets / doctor / gitignore / license / stats / deps / hooks / release / badges / contributing / config

这些命令的输入要么是一段 diff、一个文件、一份清单，要么是整个目录收集后的 prompt 材料；**没有一条命令把仓库当作有结构的对象来分析**。具体表现：

- `stats` 只给文件数 / 行数 / 语言 / 提交数，回答不了「模块怎么分层、入口在哪」
- `file-tree.ts` 只作为 prompt 内部材料存在，用户看不到
- `doctor` 检查的是本机环境与配置，不是仓库本身
- `ask` 把预算内的文件全量塞进 prompt，没有检索，也没有结构导航

### 1.3 五个结构性缺口（本期计划的直接依据）

**缺口 1：没有仓库全景视图。**
用户想快速了解一个陌生仓库时，只能 `stats` 看数字，或者读 AI 生成的 README（营销文，不是结构说明）。没有「目录树 + 模块分组 + 入口文件」的一屏总览。

**缺口 2：健康度检查各自为政。**
社区文件看 `badges`/`contributing`，密钥看 `secrets`，依赖看 `deps --outdated/--audit`，环境看 `doctor`——每项都只覆盖一个切片，没有一个命令回答「这个仓库离可维护 / 可发布还差什么」。

**缺口 3：没有结构关系。**
全仓库没有 import 图。`grep -rn "from \"" src/` 只能给出原始匹配，无法回答「改 `src/lib/git.ts` 会影响哪些文件、该跑哪些测试」。

**缺口 4：新贡献者没有上手材料。**
`contributing` 生成的是贡献规范（怎么提 PR），`readme` 是项目介绍（做什么）；没有一份「代码从哪读起、模块各自负责什么、请求怎么流转」的导读。

**缺口 5：目录遍历有三份重复实现。**

```bash
grep -rln "async function walk" src/
# src/lib/collect-files.ts
# src/lib/scan-secrets.ts
# src/lib/stats.ts
```

三个 walker 的硬跳过目录规则一致，但各写各的。新增 `map` / `health` 若再复制一份就是第四、第五份——本期应先抽出共享索引层，再在其上做命令。

**实现结果**：`src/lib/repo-index.ts` 直接复用 `collectFiles()`（唯一带敏感过滤的收集入口），没有新增第四份 walker；三份旧 walker 未强行合并——它们各自被既有测试锁定，合并的改动面与收益不成比例。

## 二 目标与原则

### 2.1 目标

1. **把仓库变成可分析对象**：一次索引同时服务地图、影响面、健康度与 AI 导读
2. **离线优先**：`map` / `impact` / `health` 不调用 LLM、不联网（`health --network` 显式开启依赖检查）
3. **零新增运行时依赖**：import 图用轻量解析实现，不引入 AST 解析器或图数据库
4. **结论可行动**：每条命令都输出「问题 + 修复建议」，而不是只给数字

### 2.2 原则

- **复用优先**：过滤规则复用 `collect-files.ts` 的常量与 `collectFiles()`；目录树复用 `file-tree.ts`；AI 材料复用 `materials.ts` / `token-budget.ts`；仓库元信息复用 `git.ts`；密钥复用 `scan-secrets.ts`；依赖复用 `npm-checks.ts`
- **不设虚假指标**：`health` 输出通过/警告/失败清单，**不合成 0–100 分**——权重无法服众，只会制造假精度
- **stdout 只放产物**：状态与进度走 stderr（`ui.ts` 既有约定）；所有新命令支持 `--json`
- **失败不写半成品**：`onboard` 落盘前做结构校验，不合格即失败
- **新增命令必带命令层测试**：不重复 6 条离线命令「lib 有测试、命令接线零覆盖」的老问题

### 2.3 明确不做（防范围蔓延）

- 真 RAG / 向量检索（需引入向量依赖，与「运行时依赖只有 2 个」冲突，单独评估）
- AI 直接改代码（保持「只给建议」）
- 非 GitHub 托管平台、GUI / 编辑器插件 / 云服务
- 符号级静态分析（跨文件类型推导、调用图）：本期只做文件级 import 图
- 性能基准与趋势存储（`health` 不做历史对比）

## 三 计划清单（按优先级）

### P0-1 `map` — 仓库地图（离线）

**问题**：缺口 1 与缺口 5。用户需要一个「一屏看懂这个仓库」的入口，且不应再复制第四个目录 walker。

**用法**

```bash
repo-ai map [path] [--depth <n>] [--focus <path>] [--json]
```

**输出（文本）**

1. 仓库基本信息：名称、git 分支与最近提交（若非 git 仓库则省略）、文件数、总行数、语言 Top 5
2. 入口文件：复用既有的入口模式（`src/index.*`、`main.*`、`app.*` 等）
3. 目录树：复用 `buildFileTree()`，按 `--depth` 裁剪
4. 模块分组：按顶层目录（`src/cli`、`src/commands`、`src/lib`、`test`……）汇总文件数与行数，帮助识别边界
5. 安全提示：经 `collectFiles()` 过滤掉的敏感文件 / 含密钥文件只报数量（`--json` 里给路径），绝不打印内容

**复用与新增**

- 复用：`collectFiles()`（过滤 + 内容读取）、`buildFileTree()`、`getRepoStats()`（数字与语言分布）、`cli/shared.ts` 的错误处理
- 新增：`src/lib/repo-index.ts`（见 P0-2）中的 `buildRepoIndex()`；`src/commands/map.ts`；`src/cli/register-offline.ts` 注册

**验收**

- fixture 仓库（三层目录 + `.env` + 含密钥的 JSON）跑 `map --json`：深度被遵守、排序稳定、敏感文件不出现在模块分组/树里
- 对本仓库跑 `map .`：能看到 `src/cli` / `src/commands` / `src/lib` / `test` 四组及入口 `src/index.ts`
- `--json` 下 stdout 只有一行 JSON；非 TTY/JSON 模式无进度噪音
- 命令层测试覆盖：非法路径退出码 1、`--depth` 边界值、`--focus` 不存在时的错误

**风险**：`getRepoStats()` 与 `collectFiles()` 各遍历一次目录——本期接受，P2 缓存项统一解决。

### P0-2 `impact` — 变更影响分析（离线）

**问题**：缺口 3。回答「改这个文件会影响谁、该跑哪些测试」。

**用法**

```bash
repo-ai impact [files...] [--diff] [--depth <n>] [--json]
```

- 无参数时默认 `--diff`（读取暂存区改动文件；无暂存改动时提示并退出 1）
- `--depth` 控制反向依赖的传递层数（默认 2）

**新增 `src/lib/repo-index.ts`（本期的共享地基）**

- `buildRepoIndex(rootDir, options)`：一次 walk 产出文件清单（路径、大小、行数、语言）、目录树与 import 边
- import 解析（正则，非 AST）：
  - JS/TS：`import ... from "..."`、`export ... from "..."`、`require("...")`、动态 `import("...")`
  - Python：`import x` / `from x import y`（尽力而为）
  - 相对路径解析：扩展名补全（`.ts/.tsx/.js/.mjs/.cjs`）与 `/index.*`；`tsconfig` paths、动态拼接的路径**不支持**，计入 `unresolved`
- `reverseDependencies(graph, targets, depth)`：BFS，处理循环
- 目录遍历规则从 `collect-files.ts` 导入（`HARD_SKIP_DIRS`、`BINARY_EXTS`），**不再复制 walker**

**输出**

- 直接依赖方、传递依赖方（按层）、受影响测试文件（`test/**`、`*.test.ts`、`*_test.py`）
- `unresolved` 计数，让用户知道解析覆盖度

**验收**

- fixture：`a.ts → b.ts → c.ts` 链，`impact c.ts --depth 1` 只列 `b.ts`，`--depth 2` 列到 `a.ts`
- 循环依赖（`a ↔ b`）不无限递归
- `index.ts` 目录解析、扩展名补全各有用例
- `--diff` 与 `git.ts` 的暂存 diff 读取打通
- **变异验证**：去掉扩展名补全或反向边，对应用例必须变红
- `--json` 字段含 `targets` / `direct` / `transitive` / `tests` / `unresolved`

**风险**：正则解析会漏掉路径别名与动态导入。对策：不宣称完整静态分析；`unresolved` 明示；已知局限写进命令 help 与 README。

### P1-1 `health` — 仓库健康审计（离线）

**问题**：缺口 2。把分散的检查汇成一份可执行的「还差什么」清单。

**用法**

```bash
repo-ai health [path] [--strict] [--network] [--json]
```

**检查项**（复用 `doctor.ts` 的 `CheckResult` 形状：`id / name / status / detail / fix`）

| 类别 | 检查内容 | 默认 |
|---|---|---|
| 社区文件 | README / LICENSE / .gitignore / CONTRIBUTING / CHANGELOG | 离线 |
| CI | `.github/workflows/*.yml` 是否存在 | 离线 |
| 测试 | 测试配置与测试文件数量（来自 repo index） | 离线 |
| 包元数据 | `package.json` 的 description / keywords / repository / engines / license | 离线 |
| 密钥 | 复用 `scanSecrets()`，只报各级别数量，**不打印命中值** | 离线 |
| 依赖 | 清单是否存在（`readDeps()`） | 离线 |
| 大文件 / TODO | 超过单文件上限的文件数、`TODO/FIXME` 计数 | 离线 |
| 依赖安全 | `npmOutdated()` / `npmAudit()` 摘要 | `--network` 才跑 |

**退出码**：存在 `fail` → 1；`--strict` 时存在 `warn` 也 → 1；否则 0。

**与既有命令的分工**（必须写进 README）：

- `doctor`：本机与工具是否就绪（Node、git、配置、key、代理）
- `health`：仓库本身是否健康（文件、CI、测试、元数据、密钥、依赖）
- `deps --audit`：只看依赖漏洞这一项

**验收**

- 完整 fixture（README/LICENSE/CI/测试/元数据齐全）→ 全部 ok
- 残缺 fixture（缺 LICENSE、无 CI、无测试）→ 对应项 warn/fail，`fix` 给出可执行命令
- `--strict` 的退出码按上表；默认不发起任何网络请求（测试中用 mock 断言）
- `--json` 输出 `checks[]` 与汇总计数；密钥只出现数量
- 命令层测试覆盖：路径非法、`--json` stdout 纯净、退出码三态

**风险**：与 `doctor`/`deps --audit` 语义重叠。对策：README 与小节互相指路；`health` 的直接输出里注明「单看依赖请用 `deps --audit`」。

### P1-2 `onboard` — 上手导读（AI）

**问题**：缺口 4。生成一份「代码从哪读起」的文档，填补 README 与 CONTRIBUTING 之间的空白。

**用法**

```bash
repo-ai onboard [path] [-o ONBOARDING.md] [--dry-run] [--stream]
                [--budget-tokens <n>] [--max-file-kb <n>] [--json]
                [--provider/--base-url/--model/--api-key/--profile]
```

**做法**

- 材料：复用 `collectMaterials()`（含敏感文件过滤与预算分配）+ `buildMaterialsSection()`；把 `repo-index` 的模块分组与入口清单作为「导航上下文」追加在材料开头
- 生成结构（写进 prompt）：一句话定位 → 架构地图 → 关键模块职责 → 数据/请求流 → 本地运行与测试 → 从哪开始改 → 常见陷阱
- 硬性约束：只引用材料中真实存在的文件路径；不编造命令；不确定的内容写 TODO
- 落盘前结构校验：新增 `src/lib/onboard-validate.ts`（参照 `readme-validate.ts`），至少含一级标题、架构/模块章节、运行/测试章节；不合格 `fail` 且不写文件
- `--dry-run`：只显示将发送的文件数、token 估算与敏感文件跳过列表，不调用 API

**验收**

- prompt 单测：导航上下文注入、结构要求、禁用编造
- 命令层打桩（沿用 `test/helpers/command-harness.ts`）：`--json` 输出形状、`-o` 落盘、`--dry-run` 不发请求、LLM 失败/结构不合格时不落盘
