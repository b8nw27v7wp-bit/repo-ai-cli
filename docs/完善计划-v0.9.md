**短板 1：配置层有 5 个只写键。**（v0.8 执行时发现，本次列为 P0-1）

```

```

`config set maxTokens | maxFileKb | maxDiffKb | maxOutputTokens | temperature` 保存成功、`config list` 显示、`src/lib/config.ts` 的 label 写着「readme 默认 token 预算」——但**没有任何命令读取它们**。用户以为设了默认值，实际命令仍走各自的 flag 默认值。这是「文档与实现不一致」里最坏的一种：命令不报错，行为静默不符。

**短板 3：`types.ts` 的 24 个 Options 接口重复同一组字段。**

| 模式 | 出现次数 |
|---|---|
| `setJsonMode(options.json === true);` | 25 |
| `if (interactive && !isJsonMode()) intro(` | 25 |
| `fail((err as Error).message);` | 33 |

| `await writeOutput(` | 12 |
| `fail("AI 返回了空内容，请重试。")` | 10 |

## 二 目标与原则

v0.8 解决的是「守住已有的」。本期解决的是**层次边界**——v0.8 把 CLI 组装层拆出来了，但配置解析仍然横跨两层、类型定义仍然靠复制粘贴。目标三条：

1. **配置层收口**：把「CLI 参数 > 配置 > 内置默认」的三层解析收敛到 CLI 层一处；命令层只接收已解析的选项，不再自己读文件
2. **消除逐字重复**：只在**逐字相同**的地方抽（类型字段、LLM 调用收尾），不为了「看起来更抽象」而合并形态各异的输出尾巴
3. **让质量可度量**：接入覆盖率，把「哪些没测到」从人肉比对变成数字与阈值

**明确不做**（防范围蔓延）：GUI / VSCode 插件、AI 直接写代码（`test`/`refactor`/`fix` 保持只给建议）、非 GitHub 托管平台、真 RAG 检索（需引入向量依赖，与「运行时依赖只有 2 个」冲突，须单独评估）、13 家 provider 端点的真机连通性验证（无 key，也不该消耗配额）、演示 GIF 录制（需人工录屏）。

## 三 计划清单（按优先级）

### P0-1 配置层收口（只写键修复 + 解析上移）

**规则**（写进 README 与 config 命令的 help）：

```
命令行显式给出  >  ~/.repo-ai/config.json（含激活 profile）  >  内置默认值
```

**关键难点**：commander 会给带默认值的 option 填上值，于是 `opts.maxTokens` 永远有值，无法区分「用户传了 48000」与「默认就是 48000」。解法是 `cmd.getOptionValueSource(key)`——返回 `"cli"` 才算用户显式给出。这样 `--help` 里的 `(default: 48000)` 得以保留（不必把默认值从 CLI 层搬到命令层，避免同一个数字出现在两处）。

**改动**：

- `src/cli/shared.ts` 新增 `resolveNumber(cmd, opts, key, cfgValue, builtin)`，一处实现三层规则
- 12 个 AI action：各加 `const cfg = await loadConfig(opts.profile)`，数值项走 `resolveNumber`
- `types.ts`：抽 `AiCommandBase`（8 个共有字段 + `resolvedConfig`），12 个 AI Options 接口继承它（同时解决短板 3）
- 12 条 AI 命令：删掉 `await loadConfig(options.profile)`，改用 `options.resolvedConfig`

**验收**：

- `config set maxTokens 8000` 后 `readme --dry-run --json` 的 `budget` 为 8000（隔离 HOME 实测）
- 显式 `--budget-tokens` 盖过配置
- 无配置时用内置默认
- `grep -rhoE '\bcfg\.[a-zA-Z]+' src/` 的每个字段都能改变可观测行为

**风险**：命令层不再读配置，若某个 `runX` 被直接调用（测试、未来 API）而没传 `resolvedConfig`，provider 解析会回退到环境变量——行为与传空配置一致，不会崩，但测试要显式传。

### P0-2 LLM 调用收尾抽取

新增 `src/lib/llm-step.ts`：

```ts
/** 调用 LLM；失败或空响应时已 fail()，返回 null 表示调用方直接 return */
export async function callLlmOrFail(
  messages: ChatMessage[],
  config: LLMConfig,
  progressBar: Progress,
  failLabel: string,
): Promise<string | null>
```

10 条命令的 ~12 行收尾收敛成 1 行 + 1 个 null 判断。流式路径（readme / changelog / ask）保留各自的 try/catch——它们的进度条语义不同（要先 stop 再开始流式输出）。

**刻意不做**：输出尾巴（`-o` 落盘 / JSON / stdout 三选一）不抽。各命令的 JSON 形状在「有 -o」与「无 -o」两个分支里字段不同（`test` 无 -o 时给 `content`、有 -o 时给 `output`），抽出来要传一堆参数，反而比重复更难读。

**验收**：10 条命令的 `fail("AI 返回了空内容，请重试。")` 收敛到 1 处；既有 436 条用例全绿。

### P1-1 覆盖率基线

- 接入 `@vitest/coverage-v8`（devDependency），`npm run coverage`
- `vitest.config.ts` 配 coverage：`include: ["src/**"]`、reporter `text-summary` + `json-summary`

**验收**：`npm run coverage` 输出数字；故意删掉一条用例能让门禁变红（变异验证）。

### P1-2 密钥检测漏报收窄

把 `LOOKS_LIKE_PHRASE`（`/^[a-z0-9]+(-[a-z0-9]+)+$/`）收窄为「**所有连字符分段都只含字母**才算人写词组」：

| 值 | 现行为 | 改后 | 判定 |
|---|---|---|---|
| `use-environment-variable` | 放行 | 放行 | 全字母 → 仍是词组 ✓ |
| `new-password` | 放行 | 放行 | 全字母 ✓ |
| `sk-live-9f3a2b7c1d4e5f60` | **放行（漏报）** | 拦下 | 含数字段 ✗ |
| `abc-def-ghi-jklmno`（原注释里的例子） | 放行 | 放行 | 全字母，仍漏报 |

最后一行说明这是**收窄而非根治**：纯字母的真密钥仍会漏。要根治得上熵值/字符类混合度启发式，误杀风险与工作量都大得多，不在本期。

**代价不对称**：多拦一个文件只是 AI 少看一个文件，漏一个密钥是把凭据发给第三方。所以宁可多拦。

**验收**：新增标定用例（上表四行各一条）；既有 `collect-files.test.ts` 全绿；更新该文件里那段「已知局限」注释。

### P2-1 README 小节顺序对齐 + docs:check 守序

- 把 README 的 `#### repo-ai-cli config` 小节移到 `release` 之后，与 `--help` 一致
- `scripts/check-docs.mjs` 新增一条：README 的 `####` 小节顺序必须与 `--help` 的命令顺序一致

这条比「命令存在性」更进一步——存在性检查挡不住「新增命令时把 README 小节插错位置」，而顺序漂移正是 v0.8 拆分时差点踩到的坑。

**验收**：`npm run docs:check` 通过；把 README 两个小节对调能让它变红（变异验证）。

| 风险 | 影响 | 对策 |

## 附录 B 不在本期范围（记录以免遗忘）

- **真 RAG 检索**：`ask` 目前是全量材料收集后塞进 prompt，受 `--budget-tokens` 硬预算约束，大仓库上答案质量会掉。做真检索需引入向量依赖，与「运行时依赖只有 2 个」的现状冲突，需单独评估
